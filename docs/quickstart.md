# Quickstart: index, search, ask

This is the **one recommended setup path**. After completing it you will have
indexed a real document and generated an answer backed by a source reference.
You do not need to start the HTTP API or demo.

## Before you begin

- A Linux, macOS, or WSL terminal.
- [uv](https://docs.astral.sh/uv/getting-started/installation/).
  The project uses Python 3.14+; uv can install a compatible interpreter.
- Docker with the Compose plugin, installed and **running**.
- An OpenAI API key with access to an answer model. Hosted requests may incur charges.
- A source checkout of this repository.

No separate `uv sync`, `pip install`, `uv tool install`, or virtualenv activation
is needed. `uv run` prepares the project's environment automatically.

## 1. Get the project

```bash
git clone https://github.com/richard-costa/rag-mtst.git
cd rag-mtst
```

All subsequent commands run from the repository root.

## 2. Start the local environment

```bash
uv run rag start
```

**First time only:** the command may create a private `.env` template and ask
you to fill in required configuration. Open `.env` and set:

```dotenv
OPENAI_API_KEY=your-private-openai-key
RAG_GENERATION_MODEL=your-available-openai-model
```

Keep the values private; do not commit `.env`. Choose an answer model available
to your account. `RAG_API_KEY` is for the **HTTP server only** and is not needed
for the direct CLI. You can leave it unset while learning the CLI.

Run `uv run rag start` again. A successful run ends with messages like:

```text
PostgreSQL ready.
Migrations complete.
Ingestion worker ready.
```

Behind the scenes, the manager starts only PostgreSQL/pgvector in Docker, applies
the schema, and launches the ingestion worker as a background process **on your
computer**. It waits for readiness. The CLI and worker use the same local staging
directory for temporary inputs, avoiding container filesystem mounts.

The first build/download and the first model request can take longer than
subsequent runs.

## 3. Index the sample document

```bash
uv run rag add docs/assets/sample.md
```

The command stages the input and queues a durable job. It waits until the worker
has extracted, chunked, embedded, and indexed the document. Expect progress
through `pending`, `running`, and `completed`, and a final message similar to:

```text
Added sample.md (1 chunks).
```

Repeating an unchanged add normally reports that the source is already indexed.
This is **not** a permanent file backup; keep the original document yourself.

## 4. Search the index

```bash
uv run rag search "support hours"
```

You should see the title `sample.md`, a chunk number, and its supporting text.
The default `window` retrieval uses embeddings to find relevant chunks and
includes nearby chunks when available.

## 5. Ask a question

```bash
uv run rag ask "When is the support desk open?"
```

Expect an answer based on the sample: **Mondays and Wednesdays, 09:00–12:00**,
followed by a reference to `sample.md`. The model's exact wording is not fixed.

The **retrieval result** is source text selected from the index. The **answer**
is generated by a model using bounded retrieved context. The **reference** tells
you which passage was supplied; it does not prove that the generated conclusion
is correct. See [how it works](how-it-works.md).

## 6. Stop, resume, or inspect

```bash
uv run rag status
uv run rag stop
```

`rag stop` stops the background worker and local PostgreSQL container. Indexed
data, conversations, originals, `.env`, and model caches remain available. To
resume later:

```bash
uv run rag start
```

**Only for a deliberate fresh start:**

```bash
uv run rag reset
```

This asks you to type `RESET`, then deletes the **local database and indexed
content**, including conversations. It does not delete original documents,
configuration, or model caches. Start again with `rag start` and reindex files.

## Common problems

| Symptom | What to do |
| --- | --- |
| `uv` not found | Install uv and reopen your terminal so `PATH` is updated |
| Docker unavailable | Start the Docker daemon/Desktop; confirm `docker compose version` works |
| `rag start` creates `.env` | Fill in the missing values and rerun; this is expected on the first run |
| Missing key/model | Check `OPENAI_API_KEY` and `RAG_GENERATION_MODEL` in `.env` |
| PostgreSQL won't start | Check whether local port 5432 is already used; the manager owns the default local database only |
| Worker fails readiness | Check `.rag-data/local-runtime/worker.log` and run `uv run rag status` |
| Job stays pending | Check `uv run rag status`; a running and ready worker is required |
| No matching passages | Index the sample first; a prior `rag reset` deletes the index |
| Provider error | Verify key, model access, network, provider availability, and billing configuration |
| `rag` by itself isn't found | Use `uv run rag`; plain `rag` is available when the project's `.venv` is active or after an optional tool installation |

The local lifecycle manager runs from a **source checkout** on Linux/macOS/WSL
and uses the default `127.0.0.1:5432` PostgreSQL connection. To connect to
another database, run a separate worker manually or follow the
[development](development.md) and [operations](operations.md) guides.
It does **not** manage the HTTP API or production deployments.
